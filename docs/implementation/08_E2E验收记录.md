# 阶段 8：初步可用 MVP 端到端验收记录

> 日期：2026-08-13
> 自动化入口：`backend/tests/test_initial_mvp_e2e.py`
> 验收方式：通过 `app.main.create_app` 创建真实 FastAPI 应用，由应用自身注册全部路由；测试未手动挂载任何业务路由。

## 1. 已自动验证的主流程

1. 运营、设计师、管理员使用各自演示账号登录。
2. 运营创建并启动商品项目。
3. 使用 Mock ERP 执行导入预览并建立外部商品映射。
4. 运营编辑商品信息卡、保存字段来源、添加商品参考图和竞品图并确认商品事实。
5. 使用确定性 Mock 完成图片分析、标题候选、SKU 文案和合规检查；所有结果均声明 `network_used=false`。
6. 运营把选定标题、SKU 和安全合规结果保存为独立内容版本并确认最终版。
7. 运营按七阶段依次完成产品类型分析、真实场景规划、主场景选择、保真提示词、Mock 生图、真实性/缩略图检查和人工确认。
8. 运营创建美工任务；美工提交第一版，运营退回，美工提交第二版，运营确认通过；两个设计版本均保留。
9. 成果报告汇总商品事实、最终内容、确认生图、第二版设计结果和审计时间线；Markdown 导出与当前最终标题一致。
10. Mock ERP 写回预览剔除价格、库存和商家编码，目标固定为草稿且 `publish=false`；运营显式确认后只更新 Mock ERP 草稿。

## 2. 已自动验证的安全门禁

- 美工和仅管理员不能确认商品卡、内容版本、生图候选、美工结果或 ERP 写回。
- 高风险合规 AI 结果不能被确认为最终内容。
- 高风险图片候选不能被任何角色确认，也会阻止后续 ERP 写回预览。
- 商品参考图必须有哈希，生图模型固定为 `gpt-image-2`。
- 测试运行时 Provider 为 `mock`、`paid_requests_enabled=false`，并拦截应用侧全部异步外部 HTTP；数据库内所有生图任务的 Provider 也必须为 `mock`。
- Mock ERP 最终记录必须保持 `published=false`，审计中不能出现商品发布事件。

## 4. 尚不能由本测试证明的范围

- 本测试只证明确定性 Mock 生图闭环，不声明真实中转站请求成功，也不产生付费调用。
- 真实中转站需另行保存不含密钥的请求/响应摘要、输出文件哈希，并由运营进行人工视觉验收后，才能声明真实生图链路通过。
- 浏览器界面仍需要人工走查布局、按钮状态、文件上传体验和刷新后的展示一致性。
- PostgreSQL 正式环境仍需执行 Alembic 升级；本自动化验收使用隔离 SQLite 数据库。
